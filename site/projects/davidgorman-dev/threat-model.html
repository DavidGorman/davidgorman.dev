Threat model

This is a static personal site, so the threat model is deliberately small. The goal is to keep the site and the server it runs on in my hands, and to make sure a compromise of any one account or service can't quietly change what visitors see.

What I'm protecting

  • Site integrity: visitors should only ever see content I published.
  • The server (web-01): an Ubuntu VM on Oracle Cloud that could be abused for other attacks if taken over.
  • The control plane: my GitHub, Oracle Cloud, Cloudflare and Tailscale accounts. Each one can change the site without touching the server.
  • Availability: nice to have, but a static portfolio being down for a few hours is low impact.

There are no user accounts, no database and no form that stores data, so there is no visitor data to steal.

Who I'm defending against

Realistically: automated internet-wide scanning, opportunistic exploitation of unpatched software, credential stuffing against my accounts, and supply-chain risk in the deployment pipeline. I'm not designing for a targeted, well-resourced attacker.

Threats and controls

ThreatControlWhy this control
SSH brute force or exploit from the internet No public SSH. Admin access only over Tailscale; port 22 closed in the cloud firewall. Removes the most-scanned attack surface entirely instead of hardening it.
Unpatched OS or Nginx vulnerability Automatic security updates (unattended-upgrades); only 80 and 443 exposed. A static site needs no application runtime, so patching the OS and web server covers most of the exposed code.
Malicious change pushed through the deploy pipeline GitHub Actions deploys as a dedicated, unprivileged deploy user that can only write the web root. Deployment reaches the server over Tailscale, so no inbound port is opened for it. Limits the blast radius: a compromised workflow can deface the site but can't take over the server.
Account takeover (GitHub, Oracle Cloud, Cloudflare, Tailscale) Unique passwords and MFA on every account; dedicated admin mailbox. These accounts can change the site or DNS without ever touching the server, so they are as important as the server itself.
Traffic interception or downgrade TLS via Let's Encrypt with HTTP redirected to HTTPS; HSTS. Prevents content injection on hostile networks.
Browser-side attacks (clickjacking, injected scripts, MIME sniffing) Security headers: Content-Security-Policy, X-Frame-Options / frame-ancestors, X-Content-Type-Options, Referrer-Policy. Cheap defence-in-depth for a site with no third-party scripts.
Domain hijack or DNS tampering Domain and DNS in Cloudflare with MFA and WHOIS privacy. Whoever controls DNS controls the site.
Data loss or a broken server Site source lives in GitHub and redeploys in minutes; boot volume backups for the server. Recovery is a rebuild, not a restore of unique data.

Residual risks I accept

  • Denial of service. A single small VM won't survive a real flood. For a portfolio, I accept that rather than adding cost.
  • Shared host. web-01 also runs Pi-hole for my private network. It is only reachable over Tailscale, but a compromise of the web server would also reach it.
  • Third-party trust. GitHub, Oracle, Cloudflare, Tailscale and Let's Encrypt are all trusted. A compromise of any of them is out of scope.
  • A compromised deploy can still deface the site. Least privilege stops it reaching the server, not changing the content.

What I'd add next

  • Require reviewed pull requests or branch protection before deploys run.
  • Pin GitHub Actions to commit hashes to reduce supply-chain risk.
  • Ship server and Nginx logs off the box so a compromise can't erase them.

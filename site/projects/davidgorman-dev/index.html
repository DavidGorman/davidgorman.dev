Overview

A portfolio written in plain HTML, CSS and JavaScript, with no frameworks, no build step and no third-party requests. It runs on Nginx on Ubuntu Server in Oracle Cloud, on infrastructure I built, secured and maintain myself.

Jump to the threat model

Problem

I wanted a portfolio I fully control, and a real public-facing server to practise securing and operating, rather than handing both off to a hosting platform.

Approach

Cloud account

  • MFA on the cloud and VPN accounts, with a separate least-privilege user for day-to-day work
  • Resources isolated in their own compartment, with IAM policies scoped to it and budget alerts to keep costs at zero

Network

  • A dedicated virtual cloud network with only HTTP and HTTPS open to the internet
  • SSH is never exposed to the internet. Everyday administration happens over a Tailscale VPN, with Oracle Cloud Bastion kept as break-glass access
  • Tailnet access controls only allow SSH to the server, from my own devices and the deploy pipeline
  • Host firewall rules mirror the cloud security list, so the server is protected at both layers

Server hardening

  • Key-only SSH, restricted to two named accounts: an admin user and an unprivileged deploy user
  • Automatic security updates
  • fail2ban banning repeated SSH failures and bots scanning for common web vulnerabilities
  • Web server version hidden from responses

TLS and security headers

  • Let's Encrypt certificate with automatic renewal, and all HTTP redirected to HTTPS
  • HSTS, a strict Content Security Policy, Permissions-Policy and other security headers
  • The site is written to work under that policy: no inline scripts or styles, and fonts are self-hosted

Deployment

  • Every push to main deploys automatically with GitHub Actions
  • The runner joins the Tailscale network as a short-lived, tagged device, so no inbound ports are opened for deployment
  • Files are deployed with rsync over SSH as a dedicated deploy user with no password or sudo, which can only write to the web root. The key is restricted and the server's host key is pinned
  • The workflow runs with read-only repository permissions

Privacy

  • Domain registration details redacted, and DNS managed through Cloudflare
  • Email routing aliases, so no personal address is published
  • The contact address only appears on the page when a visitor clicks to reveal it, keeping it away from scrapers

Threat model

This is a static site, so the threat model is deliberately small. The goal is to keep the site and the server in my hands, and to make sure a compromise of any one account or service can't quietly change what visitors see.

What I'm protecting

  • Site integrity: visitors should only ever see content I published
  • The server: a public VM that could be abused for other attacks if taken over
  • The control plane: the GitHub, Oracle Cloud, Cloudflare and Tailscale accounts, each of which can change the site without touching the server
  • Availability: nice to have, but a portfolio being down for a few hours is low impact

There are no user accounts, no database and no forms, so there is no visitor data to steal.

Who I'm defending against

Automated internet-wide scanning, opportunistic exploitation of unpatched software, credential stuffing against my accounts, and supply-chain risk in the deployment pipeline. I'm not designing for a targeted, well-resourced attacker.

Threats and controls

ThreatControlWhy this control
SSH brute force or exploit SSH is never exposed to the internet; access only over Tailscale, with key-only login Removes the most-scanned attack surface instead of hardening it
Unpatched OS or web server Automatic security updates; only HTTP and HTTPS open With no application runtime, patching the OS and Nginx covers most of the exposed code
Malicious change through the deploy pipeline Unprivileged deploy user that can only write the web root; read-only workflow permissions; pinned host key Limits the blast radius: a bad deploy can change the site but can't take over the server
Account takeover MFA and unique passwords on the accounts that control the site These accounts can change the site or DNS without ever touching the server
Interception or downgrade TLS 1.3, HTTP redirected to HTTPS, long-duration HSTS Prevents content injection on hostile networks
Injected scripts or clickjacking Strict Content Security Policy with no inline code, plus framing and MIME-sniffing protections Cheap defence in depth for a site with no third-party scripts
Server loss or corruption Source in GitHub redeploys in minutes; boot volume backups Recovery is a rebuild, not a restore of unique data

Risks I accept

  • Denial of service. A single small server won't survive a real flood. Putting the site behind Cloudflare's proxy is the planned fix
  • A compromised deploy can still deface the site. Least privilege stops it reaching the server, not changing the content
  • Third-party trust. GitHub, Oracle, Cloudflare, Tailscale and Let's Encrypt are all trusted, and a compromise of any of them is out of scope

Outcome

The site scores A+ on both the Qualys SSL Labs test and securityheaders.com, with TLS 1.3 and long-duration HSTS. One known limitation: post-quantum key exchange isn't available yet with the server's current OpenSSL version, and will arrive with a future OS release.

Next on the list is putting the site behind Cloudflare's proxy and restricting the origin so it only accepts traffic from Cloudflare.
